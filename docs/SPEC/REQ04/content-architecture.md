# REQ04 Maple Insight 기술 사례 콘텐츠 설계

[REQ04 수용 기준](../../REQUIREMENTS/REQ04.md)을 구체화한다. 이 문서는 공개 콘텐츠의 제안 구조이며, 현재 사이트의 구현 상태는 [아키텍처](../../architecture.md)를 따른다.

Phase01에서 코드·검증 기록과 대조한 사례별 주장, 이미지 선택 및 보류 근거는 [작성 개요](./case-outline.md)에 둔다.

## 독자의 이동 경로

```text
Projects 목록·포트폴리오 PDF
  → Maple Insight 프로젝트 소개 (한눈에 보는 문제·설계·상태)
  ├→ 설계 변화 글 (왜 모노레포의 경계를 다시 정했는가)
  ├→ API 타입 사례 (새 외부 API를 같은 규칙으로 추가하는 방법)
  ├→ DB 사례 (저장 책임과 관리 명령을 왜 나눴는가)
  └→ Electron 사례 (원본 데이터를 어떻게 관리·비교하는가)
각 사례 → 프로젝트 소개·관련 사례·원본 근거
```

기존 HashRouter, 블로그 Markdown/frontmatter, 목차와 관련 프로젝트 연결을 재사용한다. 프로젝트 페이지는 각 사례의 **문제·결정·현재 결과를 짧게 소개하는 입구**로 유지하고, 상세 코드는 개별 글에 둔다. 기존 설계 변화 글은 REQ03 소유 콘텐츠로 남긴다. 새 사례 추가 자체를 이유로 포트폴리오 PDF나 사이트 아키텍처를 먼저 바꾸지 않는다.

## 공통 글 구성

1. 문제 상황과 작성자의 선택: 독자가 기술 이름보다 먼저 설계 필요성을 이해한다.
2. 확인 가능한 구현: 대표 디렉터리·짧은 코드·실제 화면을 필요한 만큼 사용한다.
3. 결과와 검증: 코드 존재, 테스트, 실제 앱 검증을 서로 구분한다.
4. 한계와 다음 단계: 부분 구현과 계획을 명시한다.
5. 근거: 원본 저장소의 구체적 코드·Git 기록·REVIEW 링크를 가까이 둔다.

같은 연혁이나 프로젝트 소개를 글마다 길게 복사하지 않고 연결한다. 이미지는 도식 설명·실제 화면·ERD가 각각 답하는 질문이 있을 때만 사용한다. 모바일에서는 큰 구조 이미지의 핵심 부분을 분할하거나 읽을 수 있는 별도 SVG와 텍스트 요약을 사용한다.

### API 타입 글의 대표 장면

`ability/contract.ts`의 `/character/ability`·필수 `ocid`·선택 `date`, `params.ts`의 요청 타입, `raw.ts`의 응답 필드, `index.ts`의 재내보내기를 짧은 코드 조각과 4칸 구조 그림으로 설명한다. 기존 `basic`과 다른 범주의 API를 비교해 **규칙의 재현성**을 보여준다. 신규 API 추가 과정은 `공식 명세 확인 → 유사 구현 선택 → 네 파일 작성 → 상위 index·빌드 entry·exports 연결 → 타입 검사·호출부 검증`으로 제시한다. 실제 코드에 없는 자동 생성·주기적 감시 단계를 넣지 않는다. 공식 문서 링크를 AI 에이전트가 찾아볼 수 있지만, 현재 시작은 사용자의 수동 지시다.

카테고리별 공식 문서 링크는 사용자가 신규 API 추가를 지시했을 때 AI 에이전트가 Playwright 등으로 명세를 찾는 출발점이다. 이것은 에이전트가 활용할 수 있는 자료와 작업 방식이지, 문서 변경 감시나 코드 동기화 기능이 아니다.

발행 전 `contract.ts`의 선택 파라미터 목록과 `params.ts`의 실제 선택성도 대조한다. 예컨대 ranking/overall은 `optionalParams` 목록에 있는 필드가 `params.ts`에서 선택형으로 선언되지 않은 사례가 있어, 모든 API 정의가 공식 명세와 완전히 일치한다고 주장하지 않는다.

### DB·Electron 이미지 사용

DB 글은 검증된 패키지 의존 관계를 간결한 새 도식으로 보여주고, `app`·`ranking`·`game_data`·`equipment` ERD 중 설명하는 모델에 해당하는 것만 사용한다. 전체 ERD를 한꺼번에 축소하지 않는다. 기존 패키지 아키텍처 PNG는 `app` 설명과 트랜잭션 범위가 실제 코드보다 넓어 [작성 개요](./case-outline.md)에 공개 보류로 기록했다.

Electron 글은 IPC 경계 그림과 **버전 비교 → 직업 편집 → 스킬 목록·아이콘 추출** 중 검증 근거가 있는 대표 화면을 고른다. 화면마다 촬영 시점, 입력 또는 fixture, 실제로 확인한 조작, 아직 미완성인 부분을 캡션에 적는다. [Electron 아키텍처 참고문서](../../portfolio/maple-insight/references/electron-architecture.md)는 현재 개요 수준이므로 원본 코드와 검증 기록으로 보완한 뒤 공개 설명의 근거로 사용한다. 원본 전체 아키텍처 PNG는 모바일 가독성 때문에 보류하고 `job-data:list` 흐름만 다시 그린다.

## 공개 자산과 검증 규칙

- `docs/portfolio/maple-insight/images/`는 제작 자료다. 선정한 자산만 사이트에서 접근 가능한 위치로 복사하거나 변환하고, 원본의 출처와 설명을 유지한다. Figma 연동은 계획하지 않는다.
- 구조와 관계는 기존 SVG·Mermaid 방식부터 사용한다. 사용자 제공 PNG의 글자가 모바일에서 읽히지 않으면 핵심 흐름을 다시 그리되, 확인되지 않은 연결을 추가하지 않는다.
- 모든 글은 기존 frontmatter의 고유 slug·날짜·category·tags·`relatedProjects` 규칙을 따르고, 프로젝트 페이지에서 명시적으로 연결한다. 개별 글의 PDF는 이번 수용 기준에 포함하지 않는다.
- 화면·이미지의 비밀값·개인정보·오래된 완료 주장과 외부 GitHub 링크의 공개 접근 여부를 확인한다. 로컬 테스트 통과와 배포 URL 검증은 별개로 기록한다.
