## 소개 문안

비전공자로 개발을 배우며 React와 기본 개발 도구를 익혔고, 수료 후에는 배운 방식에 머무르지 않고 실제 불편을 해결할 도구를 찾아 적용했습니다. 제한된 저장 공간에서 패키지 중복을 줄이고 의존성 사용을 명확히 하고 싶어 pnpm을 선택했습니다. 여러 앱과 공유 패키지를 함께 관리할 방법으로 Git Submodule도 살펴봤지만 저장소별 관리 부담이 커 보여 pnpm workspace와 Turborepo를 사용했습니다. pnpm은 패키지 관리에, Turborepo는 앱·패키지의 작업 실행 순서를 관리하는 데 활용했습니다.

AI를 적극 활용한 개인 프로젝트 Maple Insight에서는 처음에 공통 타입을 공유하고, 이후 UI·유틸리티를 분리했습니다. 기능이 늘면서 코드 종류별 분리만으로는 앱 사이의 데이터 규칙을 설명하기 어려워, 외부 API 타입과 내부 데이터 계약, 게임 데이터와 계산 로직을 각각의 책임으로 나눴습니다. 프런트엔드·백엔드·데이터베이스·Electron이 함께 쓸 형식을 정의하면서도 각 앱의 역할을 구분하려는 선택이었습니다. 초기에는 Codex와 대화하고 직접 예시 코드를 작성하며 방향을 잡았습니다. 프로젝트가 커지면서 대화 기록과 README·AGENTS 문서만으로는 역할별 지침을 일관되게 찾기 어렵다는 문제를 느꼈고, 이를 작업별 Skill과 Git Hook으로 정리하는 Codex Workspace로 이어 갔습니다.

새로운 기술을 쓸 때는 소개된 장점만 믿기보다 직접 적용해 보고, 해결하려던 문제와 실제로 확인한 결과를 구분하려고 합니다. 앞으로도 기능을 만드는 이유와 구조적 선택을 설명하고, 검증 가능한 근거를 남기는 개발자로 성장하고 싶습니다.

## 작성 근거와 표현 범위

- pnpm 선택에는 저장 공간 제약과 의존성 관리에 대한 관심이 있었고, Turborepo는 여러 앱·패키지의 작업을 함께 관리하기 위해 사용했습니다. [개발 경험 기록](./maple-insight/development-history.md)과 Maple Insight의 [구조 분석](./maple-insight/architecture.md)을 참고했습니다.
- 공유 패키지의 변화는 [아키텍처 발전 과정](./maple-insight/architecture-evolution.md)에 정리된 단계와 Git 기록을 근거로 표현했습니다. 데이터 처리 속도나 코드 재사용률 개선으로 확대 해석하지 않았습니다.
- PostgreSQL 도입은 다른 관계형 데이터베이스를 배우려는 탐색이었습니다. 성능 문제를 해결한 사례로 표현하지 않았습니다.
- 설치 속도·빌드 시간·코드 재사용률을 측정한 기록이나 팀 코드 리뷰 경험은 확인되지 않아 수치와 협업 성과를 넣지 않았습니다.

- 학습 중인 기술과 커리어 목표를 현재 생각에 맞게 수정
- 성능 수치나 협업 경험을 추가할 때는 측정 기록 또는 실제 사례를 먼저 확인
