# 개발 환경 및 기술 스택 도입 배경 분석

Maple Insight 프로젝트에서 사용한 기술들의 도입 배경과 개발자로서의 성장 과정을 포트폴리오 분석 문서에 반영하고 싶습니다.

아래 내용은 사용자가 직접 경험한 기술 탐색 및 선택 과정입니다.

현재 프로젝트의 코드와 설정을 확인하고, 사용자의 실제 경험을 바탕으로 기술적 의사결정 과정과 성장 기록을 정리해주세요.

## 1. 배경: 학원 수료 이후의 기술 탐색

비전공자로 개발 학원을 다니면서 React, npm, Yarn, MySQL 등 기본적인 개발 기술을 학습했습니다.

처음에는 학원에서 배운 기술들을 중심으로 프로젝트를 개발했습니다.

그러나 학원을 수료한 이후, 기존에 배운 기술 외에도 개발 환경을 개선하거나 더 효율적으로 작업할 수 있는 도구가 있는지 적극적으로 탐색하기 시작했습니다.

이 과정에서 Vite, pnpm, Turborepo, tsup, PostgreSQL 등을 발견하고 실제 프로젝트에 도입했습니다.

당시에는 각 기술의 장단점을 깊이 이해하거나 여러 도구를 체계적으로 벤치마크한 것은 아니었습니다.

기술 소개 글, 사용 사례, 공식 문서 등에서 접한 특징을 바탕으로 관심을 갖고 직접 사용해 보는 탐색적 접근이었습니다.

## 2. 패키지 관리자: npm → Yarn → pnpm

### 초기 경험

처음에는 npm을 사용했지만 패키지 간 버전 충돌로 설치 오류가 발생하는 경험이 있었습니다.

학원에서는 이를 해결하기 위해 Yarn을 사용하게 되었습니다.

이후 Yarn 역시 의존성 버전을 강제로 조정하거나 충돌을 우회하여 설치하는 경우가 있다는 내용을 접하면서 의존성 관리의 안정성에 의문을 갖게 되었습니다.

당시에는 이러한 방식이 안전하지 않을 수 있다고 이해했지만, 실제 Yarn의 동작 원리를 정확하게 검증한 것은 아닙니다.

### pnpm 선택 이유

새로운 패키지 관리 도구를 탐색하면서 pnpm을 발견했습니다.

특히 다음 특징에 관심을 가졌습니다.

- 콘텐츠 주소 기반 저장소를 통한 패키지 재사용
- 링크를 활용한 중복 파일 저장 최소화
- 엄격한 의존성 접근 구조
- 빠른 패키지 설치 속도

개인 개발 컴퓨터는 저장 공간에 명확한 제약이 있었기 때문에, 프로젝트마다 동일한 패키지를 중복 저장하는 문제를 줄일 수 있다는 점이 특히 매력적이었습니다.

또한 당시에는 pnpm의 의존성 관리 방식이 npm이나 Yarn보다 안전할 수 있다고 이해했습니다.

### 기술적 해석 시 주의사항

npm의 버전 충돌 오류는 의존성 문제를 사전에 감지하는 정상적인 동작일 수 있습니다.

Yarn이 기본적으로 패키지 버전을 강제로 낮추는 것은 아니며, 버전과 설정에 따라 의존성 해결 정책이 다릅니다.

pnpm의 엄격한 의존성 구조는 선언하지 않은 패키지를 우연히 사용하는 문제를 줄이는 데 유리하지만, 모든 버전 충돌을 해결하거나 절대적인 안정성을 보장하지는 않습니다.

따라서 당시 사용자의 이해와 실제 기술적 특성을 구분하여 작성해주세요.

## 3. 모노레포: Git Submodule 검토 → Turborepo

### 문제 인식

개발을 배운 지 얼마 되지 않았을 당시, 서로 다른 프로젝트들을 하나의 공간에서 통합 관리하고 싶었습니다.

처음 발견한 방법은 Git Submodule이었습니다.

하지만 Git Submodule은 각각의 저장소를 별도로 생성하고 관리해야 했으며, 사용 방식도 복잡하게 느껴졌습니다.

이러한 관리 부담을 줄일 수 있는 다른 방법을 탐색하던 중 Monorepo라는 개념을 발견했습니다.

### Turborepo 선택

모노레포 관련 도구를 찾아보던 중 Turborepo를 발견했습니다.

당시 Turborepo는 비교적 새로운 도구로 소개되고 있었으며 다음 특징을 강조하고 있었습니다.

- 간단한 초기 설정
- 빠른 빌드 및 태스크 실행
- 캐싱을 통한 불필요한 작업 감소
- 여러 프로젝트의 통합 관리

다른 모노레포 도구를 깊이 비교한 것은 아니었습니다.

당시 처음 알게 된 Turborepo의 특징이 요구사항과 잘 맞는다고 판단하여 채택했습니다.

### 실제 사용 경험

도입 이후 pnpm workspace와 결합하여 여러 앱과 공유 패키지를 관리했습니다.

또한 패키지와 백엔드는 tsup, 프론트엔드는 Vite 등 서로 다른 빌드 도구를 사용하면서도 비교적 간단하게 태스크를 구성할 수 있었습니다.

실제 개발 과정에서 빠른 실행과 설정의 간결함을 체감했습니다.

단, 다른 모노레포 도구와의 성능 비교나 정량적인 빌드 시간 측정은 수행하지 않았습니다.

### 기술적 구분

단일 저장소에서 여러 프로젝트를 관리하는 것은 모노레포 구조 자체의 특징입니다.

Turborepo는 이러한 환경에서 태스크 실행, 의존성 관리, 캐싱 등을 담당하는 도구입니다.

pnpm workspace의 패키지 관리 역할과 Turborepo의 태스크 오케스트레이션 역할을 구분하여 설명해주세요.

## 4. 프론트엔드 개발 환경: Vite

초기에는 학원에서 배운 방식으로 React 프로젝트를 개발했습니다.

이후 프론트엔드 개발 환경을 탐색하면서 Vite를 발견했습니다.

당시 Vite는 빠르게 주목받는 도구였으며, 다음 특징에 관심을 가졌습니다.

- 빠른 개발 서버 실행
- 가벼운 개발 환경
- 간편한 초기 설정
- React 프로젝트와의 연계

기존 React 개발 환경보다 가볍고 빠르다는 소개가 특히 매력적으로 느껴졌습니다.

다만 React는 UI 라이브러리이고 Vite는 개발 서버 및 빌드 도구이므로, React와 Vite를 직접적인 대체 관계로 설명하지 마세요.

실제로는 기존 React 프로젝트 구성 방식에서 Vite 기반 개발 환경으로 관심을 확장한 경험입니다.

## 5. 라이브러리 및 백엔드 빌드: tsup

tsup은 pnpm, Turborepo를 탐색하던 시기에 함께 발견했습니다.

당시 세 도구는 빠른 실행 속도를 강조하고 있었으며, 함께 사용했을 때 연계가 좋다는 소개 글을 접했습니다.

이러한 특징에 관심을 갖고 세 도구를 조합하여 도입했습니다.

실제 프로젝트에서는 tsup을 패키지 및 백엔드 빌드에 활용했습니다.

현재는 tsup의 유지보수 상태에 변화가 있었지만, 프로젝트를 처음 구성할 당시에는 적절하다고 판단하여 선택한 도구였고 기존 빌드 환경에서도 사용하고 있습니다.

tsup의 현재 유지보수 상태와 프로젝트 내 사용 현황은 별도로 확인해주세요.

또한 세 도구의 조합이 다른 구성보다 객관적으로 빠르다는 벤치마크를 수행한 것은 아니므로, 검증된 성능 우위처럼 작성하지 마세요.

## 6. 데이터베이스: MySQL → PostgreSQL

학원에서는 MySQL을 학습했습니다.

이후 다른 데이터베이스 기술도 경험하고 싶어 새로운 도구를 탐색했습니다.

그 과정에서 PostgreSQL이 주목받고 있다는 내용을 접했고, 직접 사용해 보고 싶다는 생각으로 도입했습니다.

PostgreSQL을 선택한 이유는 MySQL보다 성능이 우수하거나 기술적으로 더 적합하다는 결론을 내렸기 때문이 아닙니다.

새로운 관계형 데이터베이스를 경험하고 학습 범위를 넓히려는 목적이 컸습니다.

따라서 PostgreSQL 도입을 성능 개선이나 기존 데이터베이스의 문제 해결 사례로 과장하지 마세요.

## 7. 기술 선택 과정에서 나타난 공통적인 특징

사용자가 기술을 선택할 때 반복적으로 관심을 가졌던 요소는 다음과 같습니다.

| 판단 기준                      | 관련 기술               |
| ------------------------------ | ----------------------- |
| 빠른 개발 및 빌드 속도         | Vite, Turborepo, tsup   |
| 간편한 설정과 관리             | Vite, Turborepo         |
| 제한된 저장 공간의 효율적 활용 | pnpm                    |
| 도구 간 연계와 통합 관리       | pnpm, Turborepo, tsup   |
| 새로운 기술에 대한 탐색과 학습 | PostgreSQL 및 기타 도구 |

이러한 경험을 모두 동일한 문제 해결 사례로 해석하지 마세요.

기술별로 실제 불편함을 해결하려는 선택과 새로운 기술을 경험하기 위한 탐색적 선택을 구분해야 합니다.

## 8. 개발 방식의 변화

초기에는 학원에서 배운 기술을 활용해 기능을 구현하는 데 집중했습니다.

학원 수료 이후에는 기존 기술 외에 새로운 도구를 적극적으로 탐색하고, 여러 도구를 조합하여 개발 환경을 구성하기 시작했습니다.

이후 프로젝트가 확장되면서 개발 환경뿐 아니라 코드 구조, 문서 관리, 자동화, 에이전트 활용 방식에도 관심을 갖게 되었습니다.

이러한 경험은 별도로 운영 중인 `codex-workspace` 프로젝트에서 Skill, Hook, 에이전트 지침 및 문서 관리 체계를 설계하는 방향으로 이어졌습니다.

다만 이러한 성장 과정은 사용자의 경험을 바탕으로 정리한 것이므로, 실제 시간 순서나 기술 간 연관성이 불명확한 부분을 임의로 확정하지 마세요.

## 9. 분석 및 문서화 요구사항

현재 프로젝트의 실제 코드와 설정을 확인하여 다음 사항을 분석해주세요.

1. 현재 pnpm workspace의 구성과 패키지 관리 방식
2. Turborepo의 태스크 및 캐싱 설정
3. Vite를 사용하는 앱과 실제 빌드 구성
4. tsup을 사용하는 패키지 및 백엔드의 빌드 구성
5. PostgreSQL과 데이터베이스 관련 패키지 구성
6. 각 도구가 프로젝트 내에서 담당하는 역할과 연결 관계

분석 결과를 바탕으로 기술별 도입 배경과 실제 활용 사례를 정리해주세요.

다음 원칙을 준수하세요.

- 사용자의 경험과 코드에서 확인한 사실을 구분합니다.
- 당시의 기술적 이해가 부정확했다면 현재의 정확한 설명을 함께 제시합니다.
- 사용하지 않은 기술을 사용했다고 작성하지 않습니다.
- 수행하지 않은 벤치마크나 비교 분석을 수행했다고 작성하지 않습니다.
- 성능 향상률, 디스크 절약량 등 측정되지 않은 수치를 만들어내지 않습니다.
- 실제 코드에서 확인되지 않는 효과는 추정이라고 명시합니다.
- 특정 기술이 다른 기술보다 무조건 우수하다는 표현을 피합니다.
- 기술 스택 나열보다 도입 배경과 의사결정 과정을 중심으로 작성합니다.
