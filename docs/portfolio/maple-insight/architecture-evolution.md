# Maple Insight 아키텍처 발전 과정과 개발 철학

## 1. 시작 — 더 편리한 통합 개발 환경을 만들고 싶었다

Maple Insight는 처음부터 현재와 같은 아키텍처로 설계된 프로젝트가 아니다.

여러 프로젝트를 개발하고 관리하면서 저장소와 설정이 분산되는 불편함을 느꼈고, 이를 하나의 환경에서 효율적으로 관리하고 싶었다.

처음에는 Git Submodule도 살펴봤지만, 여러 저장소를 개별적으로 관리해야 한다는 점이 내가 원하는 통합 개발 환경과는 맞지 않았다.

이후 모노레포라는 개념을 알게 되었고, pnpm과 Turborepo를 활용해 여러 애플리케이션과 공유 패키지를 하나의 저장소에서 관리하기 시작했다.

당시 기술을 선택한 기준은 비교적 단순했다.

- 여러 프로젝트를 한곳에서 관리할 수 있는가?
- 개발과 빌드 과정이 빠르고 편리한가?
- 중복된 의존성과 설정을 줄일 수 있는가?
- 프로젝트가 확장되더라도 유지보수하기 편리한가?

처음부터 완성된 아키텍처를 목표로 했다기보다는, 개발하면서 경험하는 불편함을 하나씩 해결하는 과정이었다.

## 2. 1단계 — 모노레포 도입과 기본적인 코드 공유

**Git 기록:** [초기 모노레포 구조 — 7d1dd19](https://github.com/jo4086/maple-insight/tree/7d1dd192facf112972e687036a7f640baafb3c22)

초기에는 다음과 같은 구조로 시작했다.

```text
apps/
├── back/
├── front/
└── front-end/

packages/
└── types/
```

이 시점에도 pnpm, Turborepo, Vite, tsup을 도입했고, 공통 TypeScript 설정과 기본적인 빌드 의존성 관리 기능을 구성했다.

그러나 패키지의 역할은 주로 공통 타입을 여러 애플리케이션에서 재사용하는 것이었다.

당시에는 여러 프로젝트를 하나의 저장소에 통합하고, 중복되는 코드를 공유하는 것만으로도 충분히 의미 있는 개선이라고 생각했다.

하지만 프로젝트의 기능이 확장되면서 단순히 코드를 공유하는 것만으로는 해결되지 않는 문제가 있다는 것을 점차 경험하게 되었다.

## 3. 2단계 — 공통 기능별 패키지 분리

**Git 기록:** [공유 패키지 확장 — c2f7289](https://github.com/jo4086/maple-insight/tree/c2f7289d46a7bd0961045e4a83cddada541a0576/packages)

프로젝트가 커지면서 공유 대상을 타입뿐 아니라 UI, 유틸리티, CSS 등으로 확장했다.

```text
packages/
├── css-conponents/
├── mapleInsight-types/
├── mapleInsight-ui/
└── mapleInsight-utils/
```

이 시점의 설계는 공통 코드를 종류별로 분리하고 재사용하는 데 초점이 맞춰져 있었다.

하나의 패키지에 모든 코드를 넣는 것보다 역할을 구분하기 쉬웠고, 여러 애플리케이션에서 공통 기능을 활용할 수 있는 기반도 마련했다.

그러나 개발을 계속하면서 이러한 분류가 내가 최종적으로 원하는 구조와는 다르다는 것을 깨달았다.

타입을 공유한다고 해서 프론트엔드와 백엔드 사이의 데이터 규칙이 명확해지는 것은 아니었다.

또한 UI, 유틸리티처럼 코드의 종류를 기준으로 패키지를 구분하는 것만으로는 게임 데이터와 계산 규칙, 외부 API의 데이터 구조, 애플리케이션 내부의 데이터 계약을 명확하게 표현하기 어려웠다.

결국 중요한 것은 **어떤 코드를 공유하느냐보다, 무엇을 하나의 책임으로 정의하고 공유하느냐**라는 점이었다.

이러한 경험이 이후 아키텍처를 재설계하는 계기가 되었다.

## 4. 3단계 — 코드 공유에서 도메인 공유로의 전환

**Git 기록:** [도메인 중심 아키텍처 재구성 — e0a429f](https://github.com/jo4086/maple-insight/tree/e0a429f668470c9359249b25bb7f6007bb2570b4/packages)

이 단계에서는 기존의 공유 패키지 구조를 확장하는 수준을 넘어, 패키지를 구분하는 기준 자체를 변경했다.

```text
packages/
├── api-types/
│   ├── character/
│   ├── ranking/
│   └── union/
├── contracts/
│   ├── domain/
│   ├── internal/
│   └── nexon/
├── database/
│   ├── data-admin/
│   └── db/
├── game-data/
│   ├── class/
│   ├── core/
│   ├── equipment/
│   ├── skill/
│   ├── stat/
│   └── ...
├── game-data-legacy/
├── generator/
└── simulator/
```

기존에는 타입, UI, 유틸리티와 같은 기술적 분류가 중심이었다면, 새로운 구조에서는 각 패키지가 어떤 도메인과 책임을 소유하는지가 중요해졌다.

### 외부 API 타입과 내부 데이터 계약의 분리

특히 중요하게 생각한 부분은 프론트엔드와 백엔드 사이의 데이터 규칙이었다.

Nexon Open API에서 제공하는 원본 데이터 구조와 실제 애플리케이션에서 사용하기 편리한 데이터 구조는 반드시 같을 필요가 없었다.

따라서 외부 API의 데이터 타입과 애플리케이션 내부의 데이터 계약을 구분하는 방향으로 설계했다.

- **api-types:** 외부 API의 원본 데이터 구조를 표현한다.
- **contracts:** 애플리케이션에서 사용하는 정규화된 데이터 구조와 공유 계약을 정의한다.
- **game-data:** 게임 데이터와 도메인 규칙을 관리한다.
- **database:** 데이터 저장 및 관리에 필요한 기능을 담당한다.
- **generator:** 필요한 데이터와 산출물을 생성한다.
- **simulator:** 게임 규칙을 활용한 계산과 시뮬레이션을 담당한다.

이러한 구조를 통해 프론트엔드와 백엔드가 서로 독립적으로 데이터 형식을 해석하기보다, 공통으로 정의된 계약을 기준으로 개발하는 방향을 추구했다.

또한 게임 데이터와 계산 규칙을 특정 화면이나 서버 구현에 종속시키지 않고, 여러 애플리케이션에서 재사용할 수 있는 패키지로 구성하고자 했다.

### 패키지는 단순한 공유 폴더가 아니다

이 과정에서 패키지에 대한 관점도 바뀌었다.

처음에는 공통 코드를 모아두는 디렉터리 정도로 이해했다면, 이후에는 패키지가 자신의 책임과 공개 인터페이스, 의존 관계를 갖춰야 한다고 생각하게 되었다.

이를 위해 개별 패키지의 `package.json`, `exports`, TypeScript 설정, 빌드 설정을 구성하고, 상위 패키지 그룹을 통해 관련 패키지들을 관리하는 구조를 도입했다.

루트의 공통 설정을 상속하면서도 각 패키지가 필요한 설정을 개별적으로 정의할 수 있도록 했다.

물론 이 시점에 모든 관리 체계가 완성된 것은 아니었다. 패키지 그룹별 실행 명령이나 TypeScript 설정에는 여전히 정리하고 개선할 부분이 남아 있었다.

하지만 **패키지의 개수를 늘리는 것이 아니라, 패키지의 경계와 역할을 명확히 하는 방향으로 아키텍처를 재설계했다**는 점에서 중요한 전환점이었다.

## 5. 4단계 — 아키텍처의 안정성과 관리 편의성 개선

**Git 기록:** [현재 Maple Insight 저장소](https://github.com/jo4086/maple-insight)

도메인 중심의 패키지 구조를 도입한 이후에도 개발 환경을 지속적으로 개선하고 있다.

현재는 다음과 같은 방향을 중요하게 생각한다.

### 설정의 일관성과 책임 분리

공통 TypeScript 설정은 루트에서 관리하되, 그룹과 개별 패키지의 설정을 분리해 필요한 옵션을 상속하거나 재정의할 수 있도록 구성했다.

빌드와 타입 검사도 패키지의 역할에 따라 관리하고, pnpm의 워크스페이스 기능과 필터를 활용해 필요한 작업을 실행할 수 있도록 했다.

### 애플리케이션과 도메인 로직의 분리

프로젝트가 프론트엔드와 백엔드를 넘어 Electron, 데이터 수집기 등으로 확장되면서 공통 도메인 로직을 특정 애플리케이션에 종속시키지 않는 것이 더욱 중요해졌다.

새로운 애플리케이션이 추가되더라도 이미 정의된 타입, 계약, 게임 데이터와 계산 기능을 활용할 수 있는 구조를 지향하고 있다.

Electron Data Studio를 별도 앱으로 둔 데에도 책임 분리의 이유가 있다. 웹 관리자 화면은 이용 추이와 사이트 운영에 집중시키고, 위컴알(WzComparerR2)로 준비한 CSV의 변환·검증·버전 비교처럼 로컬 게임 데이터를 다루는 일은 Electron에 맡기려 했다. 현재 웹 admin import 화면은 미연결 초안이다. Electron의 CSV→JSON 가져오기·검증·raw 버전 비교는 검증 기록이 있지만, DB 도메인 데이터의 승인 반영은 계획 단계다. [Electron 앱 분석](./applications.md), [데이터 흐름](./flows.md).

스킬 아이콘도 같은 로컬 도구의 별도 입력 경로다. AI를 활용해 C#으로 만든 추출기가 WzComparerR2의 WzLib으로 WZ 원본에서 PNG를 생성했고, 특정 전직의 실제 아이콘 추출과 Electron 목록 표시가 검증됐다. 새 직업과 스킬에 빠르게 대응하려는 방향이지만, 전체 직업 자동 추출과 Windows 설치본 연동이 완료됐다는 뜻은 아니다. [추출기 기록](https://github.com/jo4086/maple-insight/blob/main/tools/maple-skill-extractor/README.md), [Electron REQ003](https://github.com/jo4086/maple-insight/blob/main/apps/electron/docs/REQUIREMENTS/REQ003.md).

### 유지보수와 안정성

새로운 기능을 추가하는 것뿐 아니라 기존 코드와 설정이 중복되거나 서로 충돌하지 않는지도 중요하게 생각하게 되었다.

불필요한 코드를 정리하고, 패키지의 책임을 명확하게 유지하며, 변경 사항이 기존 기능에 영향을 주지 않는지 검증하는 과정을 개발의 일부로 받아들이고 있다.

현재 구조 역시 완성된 정답이라고 생각하지 않는다. 프로젝트가 성장하면서 새로운 문제가 발생한다면 기존 구조를 다시 검토하고 개선할 수 있어야 한다고 생각한다.

## 6. AI를 활용한 개발 방식의 변화

이러한 아키텍처의 변화는 AI를 활용한 반복적인 개발 과정과도 연결되어 있다.

프로젝트를 개발하면서 불편한 부분을 발견하고, 이를 해결하기 위한 구조를 고민한 뒤, AI를 활용해 구현과 수정을 반복했다.

처음부터 현재의 구조를 한 번에 만들어낸 것이 아니라, 실제 개발 과정에서 발생한 문제와 새로운 요구사항에 따라 여러 차례 설계를 변경했다.

AI가 코드 작성과 설정 변경을 도와주었지만, 어떤 문제가 중요한지 판단하고, 어떤 구조를 원하는지 결정하며, 결과가 의도에 맞는지 검토하는 과정은 지속적으로 수행해야 했다.

이 경험을 통해 AI를 단순히 코드를 대신 작성하는 도구로 사용하는 것보다, 개발자가 설계 의도와 판단 기준을 명확하게 가지고 활용하는 것이 중요하다고 생각하게 되었다.

이후에는 이러한 경험을 바탕으로 에이전트 지침, Skill, Hook, 문서 관리 체계를 별도의 `codex-workspace` 프로젝트로 관리하는 방향으로도 발전시켰다.

## 7. 개발 과정에서 형성된 철학

Maple Insight를 개발하면서 가장 크게 변화한 것은 특정 기술에 대한 지식보다, 개발 구조를 바라보는 관점이었다.

### 1. 편리함은 단순히 설정이 적다는 의미가 아니다

초기에는 빠르게 실행하고 쉽게 개발할 수 있는 환경을 선호했다.

하지만 프로젝트가 커지면서 설정이 단순하더라도 책임이 불분명하면 오히려 관리하기 어려워질 수 있다는 것을 경험했다.

지금은 초기 설정에 시간이 더 필요하더라도, 이후의 변경과 확장에 대응하기 편리한 구조를 중요하게 생각한다.

### 2. 안정성은 구조에서부터 시작된다

타입 검사를 통과하는 것만으로 프론트엔드와 백엔드 사이의 데이터 규칙이 명확해지는 것은 아니다.

외부 API의 원본 데이터와 내부에서 사용하는 데이터 계약을 구분하고, 각 패키지가 책임지는 범위를 명확하게 정의하는 것이 안정적인 개발을 위한 기반이라고 생각하게 되었다.

### 3. 패키지 공유의 핵심은 도메인과 계약이다

처음에는 중복 코드를 줄이는 것이 패키지 분리의 주된 목적이었다.

하지만 실제로 프로젝트를 개발하면서 단순히 코드를 공유하는 것보다, 여러 애플리케이션이 동일한 데이터 구조와 도메인 규칙을 공유하는 것이 더 중요하다는 점을 깨달았다.

이러한 경험이 코드의 종류를 기준으로 패키지를 나누던 구조에서 도메인과 책임을 기준으로 패키지를 구분하는 구조로 전환한 가장 중요한 이유였다.

### 4. 아키텍처는 한 번에 완성되지 않는다

처음부터 모든 요구사항을 예상하고 완벽한 구조를 만드는 것은 어렵다.

실제로 사용하면서 기존 설계의 한계를 발견하고, 필요한 부분을 개선하며, 때로는 기존 구조를 크게 변경할 수도 있어야 한다.

중요한 것은 처음 선택한 구조를 끝까지 유지하는 것이 아니라, 프로젝트의 목적에 맞는 구조를 지속적으로 찾아가는 과정이라고 생각한다.

## 8. 돌아보며

Maple Insight는 여러 프로젝트를 편리하게 통합하고 싶다는 생각에서 시작했다.

처음에는 모노레포를 구성하고 공통 타입을 공유하는 것으로 출발했지만, 프로젝트가 확장되면서 단순한 코드 재사용만으로는 내가 원하는 개발 환경을 만들기 어렵다는 것을 깨달았다.

그 결과 공유 패키지를 기능별로 확장하던 구조에서 벗어나, 외부 API 타입과 내부 계약, 게임 데이터, 데이터베이스, 계산 로직의 책임을 구분하는 아키텍처로 전환했다.

이후에도 더 편리하고 안정적인 개발 환경을 만들기 위해 패키지 설정과 빌드 체계, 문서화 및 AI 활용 방식을 지속적으로 개선하고 있다.

이 과정에서 얻은 가장 중요한 경험은 **좋은 아키텍처란 처음부터 복잡하고 정교한 구조를 만드는 것이 아니라, 실제 문제를 경험하고 그 원인을 이해하며 프로젝트의 목적에 맞게 발전시키는 것**이라는 점이다.

그리고 나에게 모노레포는 이제 여러 프로젝트를 한 저장소에 모아두는 방식이 아니라, **여러 애플리케이션이 동일한 도메인 지식과 데이터 계약을 공유하면서도 각자의 책임을 유지할 수 있도록 만드는 개발 환경**이라는 의미를 갖게 되었다.
